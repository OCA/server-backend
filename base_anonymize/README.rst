This module provides a flexible mechanism and default configuration for
anonymizing data in an Odoo database.

Unlike ``odoo-bin obfuscate``, which encrypts values with a password and
can be reversed, the overwrite is irreversible: the result is
anonymized, not pseudonymized, data.

Not to be confused with ``base_db_anonymization`` by Mint System, a
separate module with a similar name. This one has pluggable methods,
default definitions for the core modules (partners, users, bank
accounts, chatter and tracking values, mail queue, calendar, CRM,
invoices, sales, purchases, projects, Italian e-invoicing, attachments),
writes in SQL rather than record by record, and refuses to run on a
database that was not neutralized.

Use Cases / Context
===================

This module was developed because the OCA internal tools workgroup needs
access to the OCA database, but shouldn't have access to the data of OCA
members.

It should be useful in any setting where external developers need access
to a database, or for setting up test and staging instances from a copy
of production.

Configuration
=============

To configure this module, you need to:

1. Go to Settings / Technical / Anonymization / Field Definitions
2. Review fields to overwrite: every field can be overwritten by some
   method, and the overwritten records can be restricted by a domain

Domains are evaluated with three variables: ``protected_partner_ids``,
the partners of the companies, OdooBot and the public users, which the
default definitions leave untouched, ``admin_user_ids``, the superuser
and the administrator, and ``protected_user_ids``, the same plus the
public users.

Methods that take options read them from the *Options* column, a JSON
object overriding the defaults shown in *Default options*. The *Pattern
with record id* method replaces ``{id}`` with the record's id, so
``partner{id}@example.com`` gives every partner a distinct address that
cannot receive mail. The *Faker provider* method generates values with
`Faker <https://faker.readthedocs.io>`__: ``{"provider": "iban"}`` gives
valid IBANs, ``{"provider": "vat_id", "locale": "it_IT"}`` valid Italian
VAT numbers; ``kwargs`` are passed to the provider, and
``"unique": true`` avoids repeated values on columns with a unique
constraint. The default definitions use it for bank account numbers and
Italian fiscal codes; VAT numbers are emptied instead, since their
format depends on the partner's country.

Definitions for fields of modules that are not installed are kept and
simply not applied. *Recompute stored computed field* definitions
rebuild the stored copies of anonymized values (``complete_name``,
``email_normalized``, ...): give them a higher sequence than the fields
they are computed from.

The definitions for the descriptions of invoice, sale and purchase lines
are inactive by default: those descriptions often quote the customer,
but replacing them makes the documents harder to read. Activate them
(filter on *Archived*) to replace each description with the name of the
line's product, or with ``Line {id}`` on lines without product.

Usage
=====

To use this module, you need to:

1. Neutralize the database (``odoo-bin neutralize``, or a copy
   neutralized by the database manager or by Odoo.sh): the anonymization
   refuses to run on a database without the ``database.is_neutralized``
   parameter, so that it cannot overwrite production data
2. Go to Settings / Technical / Anonymization / Run Anonymization
3. Confirm you really mean it

The above is only for testing configurations on small databases: the run
happens inside a web request, and on a real-size database it outlasts
the HTTP worker's time limit (``limit_time_real``, 120 seconds by
default). Usually you would script this on a clone of the production
database, before handing it over:

::

   odoo-bin neutralize -d clone
   odoo-bin shell -d clone <<'END'
   env['ir.module.module'].search([('name', '=', 'base_anonymize')]).button_immediate_install()
   env['anonymize.wizard'].action_run()
   env.cr.commit()
   END

then dump the database and copy the file store.

The log has one line per definition, with its XML id, its domain, the
rows touched and the time taken, so that a slow definition can be
spotted.

**!!CAUTION!!** The default configuration replaces the database secret
and gives all users the same random password, stored in the system
parameter ``base_anonymize.password``. The administrator's login becomes
``admin``. If you run it from the user interface you will be logged out.
